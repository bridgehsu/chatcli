# 网络、代理与模型失败

## 目标

验证外部服务不可用时，ChatCLI 不 panic、不误执行命令，并给出可理解的反馈。

## A. 模型路由不可用

### 步骤

1. 保持 Telegram 可用，将 `router.enabled` 改为 `false`，重启 ChatCLI。
2. 打开普通 Shell。
3. 发送：

   ```text
   查看当前目录
   ```

4. 恢复 `router.enabled=true`，但填入无效 API Key 后重启，再重复步骤 2 和 3。

### 预期结果

- 未配置模型时，机器人提示无法把自然语言转换为 Shell 命令，并提示可使用 `$ 命令`。
- API Key 无效或模型返回 HTTP 错误时，机器人提示模型服务不可用或请求失败。
- 不会向 Shell 发送任何候选命令。
- 日志包含模型请求失败或非成功状态，但不得打印 API Key。

## B. 模型输出异常

### 方法

使用一个测试模型网关，分别模拟以下响应：

- 非 JSON 文本；
- JSON 缺少 `command`；
- 空命令；
- 命令包含 `rm -rf`、`sudo`、管道或重定向；
- 超时。

### 预期结果

- 所有异常响应均不会进入待确认状态。
- Bot 明确告知“未执行任何操作”或说明命令被安全策略拒绝。
- 应用继续处理下一条 Telegram 消息。

## C. Telegram 或代理不可用

### 步骤

1. 临时停止本机代理，或将 `telegram.proxy_url` 改为不可达地址。
2. 重启 ChatCLI，观察日志约 20 秒。
3. 恢复代理并再次启动服务。

### 预期结果

- 日志记录连接失败和重试，而不是出现 panic 后退出。
- 网络恢复后，Bot 能重新开始 polling 并正常处理消息。
- 不要在日志或测试截图中暴露 Bot Token。
